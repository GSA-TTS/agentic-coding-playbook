# Secure Coding Practices for AI-Assisted Federal Development

> **Version:** 0.2.0 | **Impact Level:** FIPS Moderate | **Scope:** Single-agent, internal enterprise

## Quick Reference

| Domain | Key Rules |
|--------|-----------|
| Input | Validate ALL external input server-side, parameterized queries only, allowlist over denylist |
| Output | Context-appropriate encoding, no internal details in error messages |
| Secrets | Never in source code, use approved KMS or secrets managers, rotate regularly |
| Auth | Authenticate all endpoints, server-side authorization, framework-native session management |
| Dependencies | Pin exact versions, commit lock files, no critical/high CVEs, verify package names |
| Errors | Explicit handling, structured logging, no sensitive data in logs |
| Crypto | FIPS-validated algorithms only, no custom implementations, TLS 1.2+ |
| Architecture | ADRs for design decisions, design by contract, interfaces before implementations |
| Change Safety | TDD (red-green-refactor), regression tests for bug fixes, idempotent operations |
| Size Limits | Functions ≤50 lines, files ≤400 lines, cyclomatic complexity ≤10, params ≤5 |

> **For sandboxed export bundles:** a smaller operational companion may be provided at `.agent-skills/docs/CODING-PRACTICES.md`. The present document remains the canonical maintained reference.

> **Disclaimer:** This playbook is informational only and is not authoritative federal policy, official agency guidance, or a binding control interpretation. Each agency must tailor these practices to its specific requirements, approvals, and risk posture.

This document defines secure coding practices that AI agents and developers SHOULD follow when building software in federal environments. These practices apply to all code — whether written by a human, generated by an AI agent, or a combination of both.

**Key words:** "MUST", "MUST NOT", "SHOULD", "SHOULD NOT", and "MAY" are used per [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) for consistency within this reference material. Authoritative requirements remain with the cited source material and agency policy.

## 1. AI-Generated Code: Additional Responsibilities

<!-- NIST SP 800-218A: PW.1 (Design Software to Meet Security Requirements) -->
<!-- NIST AI RMF: MEASURE 2 (AI Systems Evaluated) -->

AI-generated code requires **the same security scrutiny** as human-written code — plus additional verification steps.

### 1.1 Code Provenance

- All AI-generated code SHOULD be attributable where project practices support it (for example `Co-Authored-By` in commits)
- Developers MUST review all AI-generated code before committing
- The developer assumes responsibility for all committed code regardless of who or what generated it
- The AI agent SHOULD explain its reasoning for non-obvious implementation choices
- AI-generated code MUST NOT be deployed to production without human review and approval

### 1.2 Known Limitations

Developers SHOULD be aware that AI-generated code may:
- Contain plausible-looking but incorrect logic
- Reference APIs, libraries, or language features that do not exist or are deprecated
- Reproduce insecure patterns from its training data
- Lack awareness of agency-specific requirements not included in the prompt

Mitigation: Always verify AI suggestions against official documentation. Test edge cases. Run security scanners.

> **SSDF Mapping:** PO.1.1 (Security Requirements), PW.1.1 (Design to Requirements)

## 2. Input Validation and Output Encoding

<!-- NIST SP 800-53: SI-10 (Information Input Validation) -->
<!-- OWASP LLM: LLM01 (Prompt Injection), LLM05 (Improper Output Handling) -->

### 2.1 Input Validation Rules

All external input MUST be validated before use. External input includes: HTTP request parameters, form data, file uploads, API responses, environment variables, configuration files, command-line arguments, and database query results.

**Validation approach:**

```text
1. Define expected format (type, length, range, pattern)
2. Reject anything that does not match — fail closed
3. Use allowlists, not denylists
4. Validate on the server/backend side — never trust client validation alone
````

**Specific requirements:**

| Input Type      | Validation Required                                                   |
| --------------- | --------------------------------------------------------------------- |
| String input    | Max length, character allowlist, encoding                             |
| Numeric input   | Range check, type coercion safety                                     |
| File uploads    | Extension allowlist, MIME type check, size limit, content scanning    |
| Email addresses | RFC 5322 format validation                                            |
| URLs            | Protocol allowlist (https only), domain allowlist                     |
| File paths      | Path traversal prevention (resolve, then verify prefix)               |
| SQL parameters  | Parameterized queries only — never string concatenation               |
| Shell commands  | Avoid when possible; if necessary, use library APIs not shell strings |

### 2.2 Output Encoding

Output MUST be encoded based on context:

| Context         | Encoding                                                    |
| --------------- | ----------------------------------------------------------- |
| HTML body       | HTML entity encoding                                        |
| HTML attributes | Attribute encoding (quote-safe)                             |
| JavaScript      | JavaScript string escaping                                  |
| URLs            | URL/percent encoding                                        |
| SQL             | Parameterized queries (not encoding)                        |
| Shell           | Avoid; use APIs. If unavoidable, shell-escape all arguments |
| JSON            | Proper serialization — never string concatenation           |
| Log files       | Sanitize newlines and control characters                    |

> **Control Mapping:** SI-10 (Input Validation), SI-15 (Information Output Filtering)

## 3. Authentication and Authorization in Code

<!-- NIST SP 800-53: IA-2 (Identification and Authentication), AC-3 (Access Enforcement) -->

<!-- NIST SP 800-63: Digital Identity Guidelines -->

### 3.1 Authentication

- MUST use agency-approved identity providers where applicable
- MUST NOT implement custom password storage unless specifically authorized
- MUST enforce multi-factor authentication for privileged operations when supported by the system design
- MUST NOT store credentials in source code, configuration files, or environment variables committed to version control
- SHOULD use short-lived tokens over long-lived credentials

### 3.2 Authorization

- MUST enforce authorization checks on every protected resource access server-side
- MUST use role-based access control (RBAC) or attribute-based access control (ABAC) as appropriate
- MUST deny by default
- MUST NOT rely on client-side authorization checks
- SHOULD implement authorization as middleware or decorators, not ad hoc inline checks

### 3.3 Session Management

- MUST generate cryptographically random session identifiers
- MUST set appropriate session timeouts per agency or system policy
- MUST invalidate sessions on logout
- MUST transmit session tokens only over TLS
- MUST set Secure, HttpOnly, and SameSite flags on session cookies where cookies are used

> **Control Mapping:** IA-2, IA-5, AC-3, SC-23

## 4. Secrets Management

<!-- NIST SP 800-53: SC-28 (Protection of Information at Rest), IA-5 (Authenticator Management) -->

### 4.1 Rules

- MUST NOT hardcode secrets in source code
- MUST NOT commit secrets to version control
- MUST use approved secrets management solutions
- MUST rotate secrets on a defined schedule per agency or system policy
- MUST revoke compromised secrets immediately and rotate dependent credentials

### 4.2 Prevention

- MUST configure pre-commit or CI hooks to scan for secrets before merge or release
- MUST include common secret patterns in `.gitignore` where appropriate:

  ```text
  .env
  .env.*
  *.key
  *.pem
  *.p12
  credentials.*
  *secret*
  ```
- SHOULD use environment variables or platform-native secret injection for runtime secrets
- SHOULD encrypt secrets at rest using FIPS-validated encryption

### 4.3 If a Secret Is Committed

If a secret is accidentally committed to version control:

1. Revoke the secret immediately
2. Rotate the secret and all dependent credentials
3. Remove the secret from git history as appropriate
4. Report the incident per agency procedures
5. Audit access logs for the compromised credential

> **Control Mapping:** IA-5, SC-28, IR-6

## 5. Dependency and Supply Chain Security

<!-- NIST SP 800-218A: PS.1 -->

<!-- NIST SP 800-53: SA-12, SR-3 -->

<!-- OWASP LLM: LLM03 -->

### 5.1 Dependency Selection

Before adding any dependency, verify:

| Check                 | Requirement                                                      |
| --------------------- | ---------------------------------------------------------------- |
| Maintenance status    | Active enough for your risk tolerance                            |
| Known vulnerabilities | No unpatched critical/high CVEs without explicit risk acceptance |
| License compatibility | Compatible with federal and agency use                           |
| Adoption              | Reasonable support and maintenance posture                       |
| Dependency depth      | Minimize transitive dependencies                                 |
| Package name          | Verify exact spelling to reduce typosquatting risk               |

### 5.2 Dependency Management

- MUST pin exact versions in production where tooling permits
- MUST commit lock files
- MUST run dependency vulnerability scanning in CI/CD
- MUST update dependencies on a regular schedule
- SHOULD generate an SBOM in SPDX or CycloneDX format where practical
- SHOULD verify package signatures and checksums when available

### 5.3 Container Image Security

If using containers:

- MUST use minimal or approved base images
- MUST pin image digests, not just tags
- MUST scan images for vulnerabilities before deployment
- MUST NOT run containers as root unless justified
- SHOULD use multi-stage builds to minimize attack surface

> **Control Mapping:** SA-12, SR-3, SR-11, SA-4

## 6. Error Handling and Logging

<!-- NIST SP 800-53: AU-2, SI-11 -->

### 6.1 Error Handling

- MUST handle all errors explicitly
- MUST NOT expose internal details in user-facing error messages
- MUST use structured error types with error codes where practical
- MUST log errors with enough context for debugging
- SHOULD distinguish between expected and unexpected errors

### 6.2 Logging

What to log:

- Authentication events
- Authorization decisions
- Sensitive data access events where approved
- Administrative actions
- Error conditions and exceptions

What MUST NOT be logged:

- Passwords, tokens, or secrets
- Full sensitive identifiers unless approved and required
- Full session tokens
- Sensitive data not required for approved audit purposes

Logging format:

- MUST use structured logging where practical
- MUST include timestamp, event type, severity, identity context, and result
- SHOULD include correlation IDs for request tracing

> **Control Mapping:** AU-2, AU-3, SI-11

## 7. Database Security

<!-- NIST SP 800-53: SC-28, AC-3 -->

- MUST use parameterized queries or prepared statements
- MUST use separate database accounts for different application functions where practical
- MUST encrypt sensitive data at rest using approved cryptography
- MUST enable TLS for database connections
- MUST NOT store plaintext passwords
- SHOULD use version-controlled database migrations
- SHOULD implement row-level security where applicable

> **Control Mapping:** SC-28, AC-3, IA-5

---

## 8. API Design and Security

<!-- NIST SP 800-53: SC-7, AC-4 -->

### 8.1 API Security Requirements

- MUST authenticate all non-public endpoints
- MUST implement rate limiting on public and semi-public endpoints
- MUST validate all request bodies against a schema
- MUST use HTTPS (TLS 1.2+) for all API traffic
- MUST return appropriate HTTP status codes
- MUST NOT include sensitive data in URL query parameters
- SHOULD implement request and response logging for audit purposes where appropriate
- SHOULD use API versioning to manage breaking changes

### 8.2 CORS and Headers

- MUST configure CORS with explicit origin allowlists for authenticated APIs
- MUST set security headers appropriate to the application
- SHOULD validate `Content-Type` on all endpoints

> **Control Mapping:** SC-7, AC-4, SC-8

---

## 9. Frontend Security

<!-- NIST SP 800-53: SI-10, SC-18 -->

- MUST implement Content Security Policy headers where appropriate
- MUST use framework-provided output encoding
- MUST NOT use unsafe browser APIs with untrusted data
- MUST implement CSRF protection for all state-changing operations where applicable
- MUST validate redirects against an allowlist
- SHOULD use Subresource Integrity for externally hosted scripts and stylesheets
- SHOULD minimize third-party scripts and tracking code

> **Control Mapping:** SI-10, SC-18

## 10. Infrastructure and Deployment Code

<!-- NIST SP 800-53: CM-2, SA-10 -->

### 10.1 Infrastructure as Code (IaC)

- MUST version all infrastructure definitions in source control
- MUST use least-privilege IAM roles
- MUST encrypt data at rest and in transit by default
- MUST NOT use default credentials or passwords
- MUST enable logging and monitoring for deployed services
- SHOULD use infrastructure scanning tools in CI/CD

### 10.2 CI/CD Pipeline Security

- MUST require code review approval before merging to protected branches
- MUST run automated security scanning in CI
- MUST NOT store secrets in CI/CD configuration files
- MUST use ephemeral build environments where possible
- MUST sign release artifacts where production policy requires it
- SHOULD implement pipeline-as-code

> **Control Mapping:** CM-2, SA-10, SA-11

## 11. Architecture Discipline

<!-- NIST SP 800-53: SA-8, SA-17 -->

<!-- NIST SP 800-218A: PW.1 -->

Sound architecture requires explicit decision-making, contract-driven design, and clear boundaries. These practices help ensure that AI-assisted code fits coherently into the larger system.

### 11.1 Architecture Decision Records (ADRs)

- MUST write an ADR before making meaningful architectural changes
- MUST use a consistent ADR format
- MUST include rejected alternatives with trade-offs
- MUST require peer review of ADRs before the corresponding change merges
- SHOULD store ADRs in `docs/decisions/`

### 11.2 Design by Contract

- MUST define interface contracts before writing implementations
- MUST validate preconditions at system boundaries
- SHOULD document contracts using the language's type system, assertions, or schema validation
- SHOULD NOT rely solely on runtime validation where stronger contracts are possible

### 11.3 Separation of Concerns

- MUST enforce one-way dependency flow
- MUST NOT mix infrastructure concerns with business logic in the same unit unnecessarily
- SHOULD isolate side effects behind interfaces or boundaries that can be substituted in tests

### 11.4 Conway's Law Awareness

- MUST align service and module boundaries with ownership where practical
- SHOULD consider organizational structure when designing system architecture
- SHOULD document ownership boundaries in project documentation

> **Control Mapping:** SA-8, SA-17, CM-2, SC-3

## 12. Change Safety and Verification

<!-- NIST SP 800-53: SA-11, SI-2, SI-7 -->

<!-- NIST SP 800-218A: PW.7, PW.9 -->

Every code change should be verifiable, reversible, and safe.

### 12.1 Test-Driven Development (Red-Green-Refactor)

- SHOULD write a failing test before writing production code where practical
- MUST NOT merge code that lacks corresponding tests unless explicitly justified
- MUST run the full existing test suite before committing when feasible
- SHOULD keep each test focused on a single behavior

### 12.2 Property-Based Testing

- SHOULD use property-based testing for functions with combinatorial input spaces
- SHOULD define properties as invariants
- MAY use property-based tests to supplement, not replace, example-based tests

### 12.3 Regression Test Rule

- MUST add a regression test for every resolved defect where a test is feasible
- MUST NOT close a defect without corresponding verification
- SHOULD label regression tests for traceability

### 12.4 Snapshot and Golden Tests

- SHOULD use snapshot or golden-file tests for deterministic outputs
- MUST update snapshots explicitly and review diffs
- SHOULD store golden files in version control

### 12.5 Idempotent and Deterministic Operations

- MUST design state-changing operations to be idempotent where possible
- MUST produce deterministic output for the same inputs in core business logic
- SHOULD use fixed seeds or timestamps in tests where reproducibility matters

### 12.6 Explicit Error Signaling

- MUST surface all errors
- MUST use structured error types with error codes where practical
- MUST distinguish between recoverable and fatal errors
- SHOULD avoid error signaling that callers can silently ignore

> **Control Mapping:** SA-11, SI-2, SI-7, CP-10

## 13. Scope, Simplicity, and Maintainability

<!-- NIST SP 800-53: SA-8, SA-15 -->

<!-- CISA: Secure by Design -->

Complexity is the enemy of security.

### 13.1 KISS and YAGNI

- MUST NOT implement speculative features
- MUST prefer the simplest solution that satisfies requirements
- MUST NOT add configurability or extension points unless justified by current needs
- SHOULD ask what is the simplest thing that could work

### 13.2 DRY and the Rule of Three

- SHOULD extract shared logic only at three or more occurrences unless a clearer boundary already exists
- MUST NOT DRY prematurely
- MUST ensure extracted abstractions have clear, single-purpose interfaces
- SHOULD prefer composition over inheritance

### 13.3 Size and Complexity Guidelines

- SHOULD enforce these limits unless a justified exception is documented:

  - **Functions:** ≤50 lines of logic
  - **Files/modules:** ≤400 lines
  - **Cyclomatic complexity:** ≤10 per function
  - **Function parameters:** ≤5
- MUST justify exceptions in pull requests or equivalent change records
- SHOULD use automated linting to enforce limits in CI where practical

### 13.4 SOLID Principles

Apply these proportionally to the project's complexity:

- **SRP:** Each module, class, or function should have one reason to change
- **OCP:** Add new behavior by adding new code where practical
- **LSP:** Subtypes must be substitutable for base types
- **ISP:** Interfaces should be narrow and client-specific
- **DIP:** High-level modules should depend on abstractions, not low-level details

### 13.5 Module Boundaries

- MUST define explicit public APIs for each module where relevant
- MUST NOT import internal implementation details across module boundaries without justification
- SHOULD document module boundaries and their contracts
- SHOULD enforce module boundary violations in CI where tooling supports it

> **Control Mapping:** SA-8, SA-15, SC-3, CM-3
